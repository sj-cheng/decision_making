# robot-nuc-36 硬件分析报告

调查时间：2026-10-14  
调查对象：本机 `robot-nuc-36`（当前登录用户 `robomaster`）  
调查方式：读取本机与 NFS 上的启动脚本、udev、网卡和 USB 设备，并核对雷达是否在线。

这份报告只描述这台车现在实际接上、以及软件已经按什么方式使用的硬件。代码怎么调用这些设备，见同目录的《软件分析报告》。

---

## 1. 结论

这台车的算力是一台带 RTX 2060 的 Intel NUC。传感器和执行器进 NUC 的通道只有三条：

| 通道 | 物理接口 | 设备 | 现在是否在线 |
|---|---|---|---|
| 有线网 | `enp88s0` `192.168.1.50/24` | Livox MID-360，`192.168.1.160` | 在线，ping 通 |
| USB 3 | VIA Hub，厂商 `2bdf:0001` | 海康机器人 MV-CS016-10UC，序列号 `DA7908668` | 已插入 |
| USB 2 | VIA Hub，厂商 `0483:5740` | STM32 虚拟串口，`/dev/ttyACM0` → `/dev/serial_sdk` | 已插入 |

底盘电机、云台、裁判系统都不直接进 NUC，也没有 CAN 口。它们全部经这一块 STM32，用一条 921600 的串口送到工控机。

NUC 上没有 `/dev/video*`。海康相机不走 V4L，走海康 MVS SDK。

## 3. 机器身份

交互终端 `~/.bashrc` 里写的是：

```bash
export MACHINE_ID=36
export ROBOT_TEAM=BLUE
export ROBOT_ID=1
```

这和主机名 `robot-nuc-36`、无线地址 `192.168.30.36` 一致。按这套身份，定位会加载蓝方 1 号的初始位姿。

`/etc/robot.conf` 是 Ansible 生成的，内容是另一套：

```bash
export MACHINE_ID=25
export ROBOT_TEAM=RED
export ROBOT_ID=1
```

`/nfs/env_setup.sh` 会 source 这个文件。`/nfs/start_tasc.sh` 会先跑 `env_setup.sh`。当前较新的 `/nfs/start_tree.sh` 在每个窗格里 `source ~/.bashrc`，因此走的是蓝方 1 号、机器号 36。

定位位姿表 `vehicle_initial_poses.yaml` 的注释把蓝方 1 号标成机器号 20、红方 1 号标成机器号 25。注释和现在的主机名不是同一套编号。程序选位姿时用的是 `ROBOT_TEAM` + `ROBOT_ID`，不用 `MACHINE_ID`。bashrc 生效时，蓝方 1 号初始位置是 `[17.6, 9.2, 0.1]` 米。

迁软件之前要先固定用哪一套身份，否则初始位姿和队内编号会对错。

## 5. USB 拓扑

```text
Intel xHCI
├─ Bus 04  USB 3.x 10 Gbps
│   └─ VIA USB3.1 Hub (2109:0822)
│       ├─ Port 3  Hikrobot MV-CS016-10UC (2bdf:0001)  USB 3.2 / 5 Gbps
│       └─ Port 4  VIA USB3.1 Hub (2109:1822)          下游空闲
├─ Bus 03  USB 2.0
│   └─ VIA USB2.0 Hub (2109:2822)
│       ├─ Port 1  STM32 Virtual COM Port (0483:5740)  12 Mbps  → /dev/ttyACM0
│       └─ Port 2  VIA USB2.0 Hub (2109:4822)          下游空闲
├─ Bus 01/05  USB 2.0 根集线器，空
└─ Bus 02/06  USB 3.x 根集线器，空
```

RTX 2060 自带一个 USB 3.1 控制器（PCI `01:00.2`），当前这些设备没有挂在它上面，都在 Intel xHCI 上。

### 5.1 海康相机

| 项目 | 值 |
|---|---|
| 厂商 / 产品 | Hikrobot / `MV-CS016-10UC` |
| USB ID | `2bdf:0001` |
| 序列号 | `DA7908668` |
| 速度 | USB 3.2，5 Gbps |
| 设备节点 | 无 `/dev/video*` |
| 权限规则 | `/etc/udev/rules.d/80-drivers-SDK-2bdf.rules`，`MODE=0666`，组 `plugdev` |
| SDK | `/opt/MVS`，库 `libMvCameraControl.so` |

MV-CS016-10UC 是海康机器人 1440×1080 彩色全局快门 USB3 工业相机。代码里没有再写死分辨率，实际输出以相机内部已保存参数为准。现在只插了一台。

### 5.2 STM32 串口

| 项目 | 值 |
|---|---|
| 描述 | STMicroelectronics STM32 Virtual ComPort |
| USB ID | `0483:5740` |
| 序列号 | `206E32914232` |
| 速度 | USB 全速 12 Mbps |
| 设备节点 | `/dev/ttyACM0` |
| udev 别名 | `/dev/serial_sdk` → `ttyACM0` |
| 规则 | `/etc/udev/rules.d/roborts.rules` |
| 波特率 | 软件打开时设为 921600 |

这条串口同时承载底盘、云台、裁判系统。底层协议是 RoboMaster SDK（`roborts_sdk`），不是直接的 CAN 帧。

`roborts.rules` 里还为思岚雷达留了规则：CP210x（`10c4:ea60`）的 `ttyUSB*` 会链到 `/dev/rplidar`。当前没有插入这类设备。

## 6. 雷达：Livox MID-360

| 项目 | 值 |
|---|---|
| 型号 | Livox MID-360（配置里 `lidar_type: 8`） |
| 雷达 IP | `192.168.1.160` |
| 主机 IP | `192.168.1.50`（必须是这块有线网卡） |
| 连接 | 网线直连或同网段交换机，UDP |
| 点云类型 | `pcl_data_type: 1`，笛卡尔高精度 |
| 扫描模式 | `pattern_mode: 0`，非重复扫描 |
| 配置文件 | `/nfs/SYL/RSG_Localization/src/livox_ros_driver2/config/MID360_config.json` |
| 本机副本 | `/home/robomaster/SYL/MID360_config.json`，内容与 NFS 一致 |

端口：

| 数据 | 雷达端口 | 主机端口 |
|---|---|---|
| 命令 | 56100 | 56101 |
| 推送消息 | 56200 | 56201 |
| 点云 | 56300 | 56301 |
| IMU | 56400 | 56401 |
| 日志 | 56500 | 56501 |

配置里的外参是单位阵、平移 0。雷达到云台的安装关系不在这份 JSON 里，而在定位代码里写死，见第 8 节。

驱动 launch 还写了一个广播码白名单 `47MDL9B0020057`。IP 能 ping 通只说明链路在；如果这个广播码和雷达机身不一致，驱动可以不出点云。换雷达时要改这个白名单。

MID-360 自带 IMU。当前定位用的就是这颗 IMU，没有另插独立 IMU。

## 7. 底盘、云台、裁判

NUC 侧只能看到一块 STM32。固件上报的执行器包括：

- 底盘 4 个电机（`motor1`–`motor4`）
- 底盘陀螺仪角、角速度、xy 位置和速度
- 遥控辅助通道 `aux_rc_ch1`–`ch4`、两个开关、在线标志
- 电池百分比和电压
- 云台 yaw 电机、pitch 电机
- 拨弹电机（`turn_motor`）
- 摩擦轮
- 裁判系统：比赛阶段、双方 1–5 号血量、自身血量、云台/底盘/发射机构使能、最近弹速、最近受伤

这些量都从同一条串口上来。NUC 不直接给电机发 CAN。

软件侧的速度上限（再往下发给固件之前）：

| 量 | 上限 |
|---|---|
| 底盘前后 `vx` | ±1.5 m/s |
| 底盘左右 `vy` | ±1.5 m/s |
| 底盘自旋 `vw` | ±300 °/s |
| 云台 yaw 角速度 | ±960 °/s |
| 云台 yaw 增量角 | ±90 ° |

## 8. 安装关系

这些数来自代码里的外参，不是这次重新测量的机械尺寸。

```text
map
 └─ world                 场地系。蓝方 1 号初始位姿钉在这里
     └─ odom
         └─ base_link     底盘
             └─ gimbal    只有 yaw，平移 z = 0.15 m
                 └─ camera
                     相对 gimbal：x = 0.1 m
                     yaw = -90°，pitch = 0，roll = -90°

livox_frame
    在定位代码里挂到 gimbal：
    平移 z = 0.46 m
    旋转 diag(1, -1, -1)，即绕 X 轴 180°
```

来源：

- `base_link → gimbal`：`gimbal.cpp` 的串口回调，实时发 TF。pitch 不进这个 TF。
- `gimbal → camera`：`base.launch` 里的静态 TF  
  `0.1 0.0 0.0 -1.5707963 0.0 -1.5707963 gimbal camera`
- 雷达相对云台：`multi_vehicle_localization_yaml.cpp` 的 `define_lidar2gimbal()`
- faster-lio 里 IMU 相对雷达的初值约 `T = [0.042, 0.023, -0.028]` m，并打开了在线估计。这是雷达内部 IMU，不是相对车体的安装尺寸。

蓝方 1 号场地初始位姿（`vehicle_initial_poses.yaml`）：

```text
position: [17.6, 9.2, 0.1]
rotation0: diag(-1, -1, 1)    # 绕 Z 轴 180°
```

## 10. 供电和实时性

控制节点如果以 root 运行，会把调度设成 `SCHED_FIFO`、锁内存，并把线程绑到 CPU 0。Docker 用了 `--privileged` 和 `-v /dev:/dev`，所以容器里能打开串口和相机。普通用户跑同一个节点时，代码只打印提示，不会设实时优先级。

电池电压、电机在线由 STM32 上报，NUC 不直接采样电源。
