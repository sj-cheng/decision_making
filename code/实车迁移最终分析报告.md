# 追逃博弈决策逻辑迁移到实车的最终分析报告

日期：2026-10-15  
审阅范围：`code/problems/example8.py`、`code/cpp/problems/example8.hpp`、`code/solvers/c_puct.py`、策略网络代码，以及《软件分析报告》《硬件分析报告》《实车迁移计划》。

## 结论

这个项目可以迁移到真实小车上。可以保留的核心是 C_PUCT/MCTS、策略网络的前向推理、四车博弈状态接口和动作输出形式；不能直接照搬的是仿真器里的坐标、障碍物、速度、动力学、捕获半径和终止条件。

“没有全球绝对坐标”本身不是阻碍。当前算法不需要某个固定的地球原点，但它要求四辆车、障碍物、边界和捕获判定使用**同一个共享坐标框架**。这个框架可以是：

- 当前定位链路提供的 `map`；
- 以队长车或临时锚点建立的虚拟坐标系；
- 通过 UWB、AprilTag、视觉、雷达跟踪或车间相对测距构造的共享相对坐标系。

如果每辆车只有自己的原点和自己的朝向，彼此之间没有位姿变换或相对测距，那么当前的四车 Example8 不能直接运行。单车阶段可以用自车局部坐标验证动作执行和安全层，但 Example8 的其余机器人状态仍需由虚拟数据或共享观测提供；完整 2v2 追逃必须先解决跨车坐标对齐，或者改成以自车为中心的输入并重新训练网络。

推荐路线是保留现有网络和 C_PUCT，先建立一个不依赖地理绝对原点的“虚拟共享坐标系”。这条路线的工程风险明显低于重写状态编码并重新训练策略。

## 当前代码真正依赖什么

| 模块 | 当前实现 | 对实车的含义 |
|---|---|---|
| 联合状态 | 29 维，前 8 维是 E1、E2、P1、P2 的二维位置，随后是时间、active、速度、加速度 | 四车位置必须来自同一坐标系；不能把四个独立局部坐标直接拼接 |
| 状态范围 | 所有位置限幅为 `[-10, 10]` | 这是旧网络的输入分布和边界，不是实车场地尺寸；扩大范围后不能继续无条件使用旧权重 |
| 策略输入 | 264 维：8 个自身特征 + 64 束、4 通道语义激光 | 自身 `x/y` 被按 `[-10,10]` 归一化，激光方向固定在算法坐标轴；输入不是旋转、平移不变的 |
| 障碍物 | Example8 内置 4 个矩形 | 必须替换为实车点云生成的实时矩形快照；不能把仿真矩形搬到真实场地 |
| 动作 | 每个机器人二维 `relative_position_delta`，仿真步长 `dt=1 s` | 输出应解释为未来约 1 秒的算法系位移，再转换为车体系速度；实车必须由执行器和安全层提前打断 |
| 动力学 | C++ 搜索中为单积分器，`位置 += 动作`，每步速度和加速度清零 | 不代表底盘真实动力学；真实速度、加速度、制动距离要由执行层和安全层负责 |
| 捕获 | 追捕车与逃逸车中心距 `< desired_distance`，当前为 1 m；按距离贪心一对一匹配 | 需要按车体尺寸和实际任务定义重新标定，并增加观测质量、时间滞回和事件一致性 |
| 终止 | 越界、碰障碍、时间到、某一方全部失活 | 实车的定位丢失、通信中断、雷达失效不能伪装成 `active=0` |

代码证据：`example8.py:411-515` 定义了 4 车、29 维状态、`dt=1`、速度范围和 `[-10,10]`；`example8.py:620-635` 把自身绝对位置送入网络；`example8.py:707-767` 用固定算法轴生成语义激光；`example8.py:1117-1142` 实现捕获配对；`example8.py:1251-1262` 实现终止判断。C++ 的对应逻辑在 `cpp/problems/example8.hpp` 中重复存在。

Example8 固定 `num_robots=4`、两名逃逸者和两名追捕者。单车或两车阶段不能简单删除状态字段；要么用合法的虚拟占位状态并明确标记其来源，要么另行训练 1v1/多车模型。实车中的一台车丢定位也不能直接让整个仿真状态越界终止，应由状态适配器把它标记为 `pose_lost` 并触发降级或停车。

## 没有全局坐标时，三种可行方案

### 方案 A：保留现有网络，使用共享虚拟坐标系（推荐）

选一辆队长车、比赛开始位置或一个临时锚点作为原点，定义一个稳定的共享 `SE(2)` 坐标系。每辆车把自己的局部位姿、队友位姿和点云转换到该坐标系，再使用原来的 29 维状态和 264 维编码。

这里的原点不需要是全球绝对位置，只要满足以下条件：

1. 四辆车使用同一个原点和同一个轴向；
2. 位姿变换在一局内连续、可校正；
3. 所有车辆和障碍物都经过同一组旋转和平移变换；
4. 结果落在旧网络的 `[-10,10]` 窗口内。

这是对现有算法改动最少的方案。当前车上的 `/robot_pose` 已经是 `map` 下的 `base_link`，可以直接作为第一阶段实现；`/odom` 是会漂移的底盘里程计，不能作为长期共享坐标。若不用 `map`，则需要补充车间相对定位和通信。

虚拟锚点的方向也不能每辆车各自随意选择。由于旧网络的 `x/y` 和 64 束方向有方向性，首帧锚点的轴向要和训练坐标约定校准；如果实际场地方向与训练分布差异很大，需要做旋转增强或重新训练。第一版状态中的速度、加速度应按 C++ 搜索的约定置零，实测速度只用于安全层和日志；若要把实测速度写回 29 维输入，应先验证分布或重新训练。时间字段按完成的决策步递增，不能直接填墙钟秒数。

### 方案 B：完全改成自车中心的相对状态并重新训练

可以把每个机器人的位置改为相对于当前决策车的位置，把障碍物改为相对点云，把边界通道改为局部可观测边界或未知区域，并对所有方向做旋转增强或采用旋转不变编码。

这不只是减去一个原点：现有网络还使用绝对 `x/y`、固定算法轴的 64 束激光、固定边界通道和 29 维价值输入。因此需要重写编码、训练数据和策略权重，属于新的算法版本。它适合后续研究，不适合作为第一辆实车的落地路径。

### 方案 C：各车完全独立、没有相对定位或通信

单车局部避障或单车追踪可以做；四车联合 C_PUCT 不可行。因为无法可靠构造四车 29 维状态、统一障碍物位置、统一目标身份，也无法让两队对捕获结果达成一致。

## 实车如何判定“抓捕成功”

当前仿真规则是：对所有活跃的追捕车和逃逸车计算中心距，若 `d < 1 m`，按距离从小到大做贪心一对一匹配，然后把配对双方的 `active` 设为 0。这个规则只需要相对位置，不需要全球绝对原点：

```text
r_pe = p_evader - p_pursuer       # 在追捕车局部坐标中也可以
d    = ||r_pe||
```

但真实系统不能把一次距离小于阈值的观测直接当成捕获。应新增一个独立的捕获状态适配器：

1. 接收带时间戳的敌我相对位姿、距离、目标 ID 和置信度；
2. 用车辆外形和安全余量确定 `R_capture`，不要直接沿用 1 m；中心距 1 m 可能已经意味着两车碰撞；
3. 要求 `d < R_capture` 持续若干帧或若干时间，并检查跟踪质量和相对速度；
4. 多车同时接近时，在一个共享事件管理器里做全局一对一匹配；
5. 通过队内通信广播捕获事件和序号，让两队对 `active` 的变化使用同一版本；
6. 将“暂时看不到”“通信中断”“定位失效”分别记录为 `track_lost`、`pose_lost` 或 `通信故障`，不能改写成捕获；
7. 如果任务定义的捕获是裁判系统的命中或掉血，就以 `/control/referee_info` 的真实事件为最终依据，距离规则只作为接近或预测触发条件。

还要注意，当前 Python/C++ `step()` 在 1 秒动作结束后才检查一次距离。两车如果在这一秒内相交、随后又分开，仿真规则也可能漏判。实车应使用连续传感器观测，或在动作执行期间计算相对轨迹的最小距离；必要时缩短决策周期，不能只看 1 秒终点。

推荐状态机为 `ACTIVE → CANDIDATE → CAPTURED`，并加入滞回和超时；捕获确认前可以降速或停车，但不能提前把机器人从博弈状态中删除。

## 哪些部分可以复用，哪些必须重做

可以直接复用：

- C_PUCT/MCTS 的树搜索流程；
- 策略网络的前向推理和 264 维输入接口；
- 四车动作索引、队伍掩码和基本博弈轮换逻辑；
- `relative_position_delta` 到二维速度指令的上层语义。

必须新增或替换：

- 局部位姿到共享算法坐标的状态适配器；
- 队友和敌车的身份、时间戳、置信度及丢失管理；
- 点云到算法系矩形障碍的聚类、地面过滤、自车/队友剔除和快照机制；
- 捕获事件适配器和跨车一致性协议；
- 车体尺寸、制动距离、未知区域和突发障碍安全层；
- 算法系位移到 `/control/cmd_vel` 车体系速度的航向转换；
- 真实速度、加速度和执行误差参数。

速度必须以实车测量为准：仿真中的 `0.8–1.0` 和 `1.0–1.2 m/s` 只是训练场景参数，不是底盘保证值。上车前应测量每辆车的最大速度、加速度、减速度、转向响应、滑移和停止距离，并在动作执行器与安全层中限幅。

不能直接复用：

- `Example8` 中的四个硬编码障碍矩形；
- `[-10,10]` 之外的场地假设；
- 仿真的 `0.8–1.0 m/s` 逃逸速度、`1.0–1.2 m/s` 追捕速度；
- 1 m 中心捕获距离；
- 仿真边界和“未命中激光即为空旷”的解释；
- Python MINCO 轨迹作为真实底盘控制器。C++ 搜索使用的是单积分器，实车要由独立执行和安全进程补足。

另一个必须修复的工程问题是障碍物更新：`C_PUCT._problem_wrapper_for()` 按 Python 对象缓存 `Problem_Wrapper`，初始化时复制 `obstacles`。运行中只修改 `problem.obstacles` 不会更新 C++ 搜索。应增加显式的 `update_obstacles()`，并在每次搜索开始时冻结一份障碍快照。

还要在上车前锁定网络部署路径。当前 C++ `Policy_Network_Wrapper` 只对 `"gaussian"` 建立有效的策略实现；普通 `PolicyNetwork` 的 `eval()` 返回空结果，而 Python 的确定性策略类也没有给出可供该 wrapper 识别的名称。现有 Gaussian C++ 推理还会在均值上加入 `0.1` 标准差的随机扰动，再做动作限幅。实车不能默认接受这个随机抖动：应补充确定性策略 wrapper，或明确固定 Gaussian 推理模式并评估噪声对安全和捕获的影响。部署前还要确认 CPU PyTorch、pybind ABI、checkpoint 的 264 维输入和网络层尺寸完全匹配。

即使 checkpoint 的输入维度匹配，它也只证明算法接口可运行。当前模型是在固定仿真障碍、完整状态和理想执行器上训练的；实车点云漏检、矩形近似、遮挡、延迟、滑移和局部视野都会造成分布偏移。旧模型应作为基线，经过影子运行、低速闭环和实车数据微调或域随机化后，才可评估真实任务性能。

搜索对象和 C++ wrapper 也应只在一个决策进程中使用。当前搜索调用会占用 Python GIL，缓存对象不是为多线程并发设计的；不要把同一个 solver 在多个 ROS 回调线程中并行调用。坐标窗口、速度限幅、捕获距离等参数在首次建树前固定，运行中改变后要重建 wrapper，而不是只改 Python 属性。

实车入口还必须在第一次搜索前显式清空或替换 Example8 默认的四个仿真矩形；否则它们会被复制进 C++ `Problem_Wrapper`。`torch.load` 应按 CPU 设备加载模型，模型路径应基于入口脚本解析而不是依赖 ROS/Docker 的当前工作目录。搜索预算要在目标 NUC 上实测；桌面参考测试表明带网络的 `1000×100` 搜索可能超过 1 秒，第一轮应从较小的 simulations/depth 开始，再逐步增加。

## 推荐的实车软件结构

```text
传感器/定位
    ├─ 局部位姿、相对位姿、目标跟踪
    └─ 原始点云
            ↓
共享坐标与状态适配器
    ├─ 29 维联合状态
    ├─ 敌我身份和 pose_lost/track_lost
    └─ 算法系障碍矩形快照
            ↓
捕获事件管理器 ──→ active 状态和事件序号
            ↓
C_PUCT / 策略网络
            ↓
动作执行器：算法系 Δ/1 s → 车体系 vx、vy
            ↓
独立安全层：近障、未知、定位/通信/电机故障、急停
            ↓
/control/cmd_vel（20–50 Hz，最长执行 1 s，主动发零）
```

决策程序不要自己打开 `/dev/serial_sdk`、Livox UDP 端口或海康相机；应通过现有 ROS 话题接入。测试时必须停掉规划、行为树和其他自主速度源。当前底盘速度是车体坐标，动作发布前必须使用当前航向转换；Example8 状态本身没有航向字段。

## 建议的落地顺序

1. **车端接口验证**：确认 `/robot_pose`、点云、底盘状态、TF 的频率、坐标系和时间戳；固定每台车的队伍和编号，不要依赖 `MACHINE_ID` 的旧配置冲突。
2. **单车无电机推理**：在一个虚拟共享坐标系中构造 29 维状态，验证旧 checkpoint、264 维编码、C++ bindings 和策略耗时。
3. **单车低速执行**：只执行四个方向的短动作，验证算法坐标到车体系的旋转、1 秒超时、主动停车和实测位姿回写。
4. **在线障碍适配**：用点云生成矩形并只做调试显示，确认地面、自车、队友和未知方向不会被误当作障碍或安全空旷。
5. **冻结快照接入搜索**：加入 `update_obstacles()`，一轮 `policy()` 使用同一份障碍，安全层继续独立工作。
6. **两车再四车**：先用外部状态接口验证联合状态和动作路由，再逐步替换为真实敌我跟踪；捕获事件由统一管理器广播。
7. **真实数据微调/重训**：加入局部视野、遮挡、漏检、延迟、提前打断、速度饱和、航向误差和车体外形。如果实际运行区域超过 20 m × 20 m，重新定义状态范围并重训，不能只改 `state_lims`。

每一步都要记录：输入状态来源、坐标变换、动作搜索耗时、命令执行时间、实际位移、障碍快照时间戳、捕获候选和最终事件。搜索超过执行周期时应降低 simulations/depth，不能延长上一条速度。

进入闭环前增加一项绑定验收：对同一份 29 维状态和同一份障碍快照，逐元素比较 Python 与 C++ 的 264 维 `policy_encoding()`；同时核对四个机器人策略 checkpoint 的首层输入维度和版本。队长的 C_PUCT 搜索仍会模拟对手分支，因此即使只发布本队动作，也要加载与训练协议一致的四个策略模型；每台执行器只取自己的 `algorithm_index` 动作。

## 难度和是否值得做

| 目标 | 难度 | 判断 |
|---|---:|---|
| 单车复用策略网络并输出底盘动作 | 中 | 主要是 ROS 接口、坐标旋转、实时执行和安全层 |
| 两车共享虚拟坐标并闭环追踪 | 中高 | 需要相对定位、目标身份、障碍和捕获状态机 |
| 四车 2v2、无外部全局定位但有共享相对定位 | 高 | 算法可保留，工程上要解决通信一致性、观测延迟和失联降级 |
| 四车各自局部坐标、无相对定位/通信 | 不可直接落地 | 必须先增加共享定位，或重写输入并重新训练 |
| 完全改成自车中心策略 | 很高 | 需要新的状态编码、训练分布、网络权重和验证体系 |

最终建议：先按“虚拟共享坐标系 + 现有 C_PUCT/策略网络 + 独立安全层”做单车和两车验证。只要能得到稳定的跨车相对位姿，就不需要场地的全球绝对原点；如果连跨车相对位姿也拿不到，就先不要进入四车实验，因为问题不在 MCTS，而在状态不可观测和事件无法一致判定。
