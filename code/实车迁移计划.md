## 1. 已确认的前提

`[-10, 10]` 是 `Example8` 的算法坐标框，不是场地坐标，也不是障碍物必须待的物理位置。现有代码用它做三件事：

1. `is_valid()` / `is_robot_state_valid()` 判断车是否越界，越界即终局并给 `-1` 奖励；
2. 语义激光的第 4 通道，边界矩形就是这个框；
3. `self_lidar_features()` 把自身位置按这个框归一化后送进策略网络。

因此送进 29 维状态和 `m_obstacles` 的数，必须已经落在这个框里。真实 `/robot_pose` 可以是 `(17.6, 9.2)`，转换之后才能写入状态。

车上没有可以抄进 `Example8.obstacles` 的场地障碍物表。

- 定位只提供共用场地系 `map`，以及各车出生点。红方出生 `x = 0.5`，蓝方出生 `x = 17.6`，`y` 约 `1.7` 到 `9.2`。出生点跨度大约 17 米 × 8 米。
- `/lidar/pointcloud` 由 `livox_calibration` 在 `map_enabled=true` 时发布。输入是 `/livox/points`，经过地面过滤、区域裁切、`T_map_gimbal * T_gimbal_lidar`，`frame_id` 设为 `map`。这是在线单帧点云，不是事先画好的地图。
- `rsg_planning` 的 `map_size = 10 m × 10 m` 是局部栅格缓存。`moving_obstacles` 是摇杆假障碍。两者都不能当作场地几何。

Faster-LIO 的 `blind = 4` 只作用于定位用的点云。`/lidar/pointcloud` 来自 `/livox/points`，近距离点还在，但发布前有地面过滤、裁切和统计离群点删除。阶段 0 要把这几步的实际范围记下来。近距离安全不要只靠这一路；安全层同时看 `/livox/lidar` 或 `/livox/points`。

C++ `example8.hpp::step` 的积分是 `位置 += 动作`，`Fc = 0`、`Bc = I`。搜索不走 Python 的 MINCO。每步之后 C++ 会把速度和加速度清零，所以滚树时的动力学不使用速度状态。`dt = 1` 表示这条世界系位移对应 1 秒。

`Problem_Wrapper` 按 Python 对象 id 缓存。只改 `problem.obstacles` 不会进入已经建好的 C++ 场景。

## 2. 目标数据流

```text
/robot_pose、队友位姿          map 坐标
/lidar/pointcloud              map 坐标，单帧
        |
        |  四车共用的同一组 R、t，只平移和旋转，不缩放
        v
算法坐标，落在 [-10, 10]
        |
        +--> 29 维 GameState
        +--> 本轮障碍矩形 SceneSnapshot
        |
        v
C++ Example8 + C_PUCT + 264 维策略编码
        |
        v
世界系相对位移 Δx、Δy
        |
        v
用算法系 yaw 转到车体 vx、vy，wz = 0
        |
        v
独立执行进程：最多保持 1.0 秒
        |
        v
独立安全进程：可提前打断
        |
        v
/control/cmd_vel
        |
        v
rsg_control -> /dev/serial_sdk -> STM32
```

最终不是把真实障碍物搬进 `[-10, 10]` 这个物理区域，而是把场地中的车和局部障碍，用统一刚体变换写成 `Example8` 能读的算法坐标。`[-10, 10]` 是旧权重能直接使用的运行窗口。

## 3. 全程约束

这些约束从阶段 0 开始生效，后面每个阶段都要满足。

### 3.1 不碰已经独占的设备

决策进程不打开 `/dev/serial_sdk`，不绑定 `192.168.1.160` 的 Livox 端口，不调用海康 `MV_CC_OpenDevice`。底盘用 `/control/cmd_vel`。点云用 `/lidar/pointcloud`，安全层另订阅 `/livox/lidar` 或 `/livox/points`。敌车感知在最后阶段之前不打开相机。

### 3.2 车上同时只能有一个自主速度源

`/nfs/start_tree.sh` 会拉起规划和行为树。规划发 `/control/cmd_vel_acc`，和 `/control/cmd_vel` 写入同一组底盘速度。测试决策时停掉 `pl_cont` 和 `bt_cont` 的速度输出，并确认没有节点在发 `/control/cmd_vel_aux`。遥控器辅助通道仍会叠加，试验时开关拨到不介入。

云台协调默认是底盘主动。决策第一版发布 `wz = 0`。试验前把协调模式固定成一种，避免协调器改写自旋。算法状态里没有航向，车头朝向不由 C_PUCT 决定。

### 3.3 坐标

```text
p_algorithm = R * p_map + t
```

`R`、`t` 对四辆车、点云、障碍矩形相同，写在一份配置里，不在每辆车上各自以自己为原点。不缩放。不把 `state_lims` 改大后继续加载旧 checkpoint。

出生点跨度约 17 米 × 8 米，平移后可以放进 20 米 × 20 米，余量不大。若实际要跑的区域长于 20 米，例如完整约 28 米赛场，旧网络覆盖不了。第一阶段把实验区域限制成算法框在场地上的那块 20 米 × 20 米像。要覆盖整场再重新训练。

语义激光的边界通道就是这块窗口的边界。窗口外的围墙不会出现在第 4 通道里。窗口内的墙、桩、车，来自本轮点云矩形。

### 3.4 动作合同

一条动作表示：算法系速度 `v = Δ / 1s`，车体上最多执行 1.0 秒。

- 到 1.0 秒必须置零，不能因为下一次搜索还没结束就继续走。
- 可以提前停。提前停不是一次完成的 1 秒动作。
- 搜索超过 1 秒时，先减小 `number_simulations`（现为 1000）和 `search_depth`（现为 100），不延长上一条速度。
- 低层重发 20–50 Hz，和搜索分进程。`cpp_search` 不释放 GIL。
- 底盘限幅仍是 `vx/vy ±1.5 m/s`、`wz ±300 °/s`。网络动作限幅更紧：逃逸约 `±0.8–1.0 m/s`，追捕约 `±1.0–1.2 m/s`。发布前取两者中更小的。
- 超过 1 秒没有 `/control/cmd_vel`，现有底盘节点自己会清零。执行进程仍要主动发零，不依赖这个超时。

### 3.5 中断和根状态

安全层或人工急停在 1 秒内打断时：

1. 立即发零速度；
2. 记一次 `interrupted`，记下已执行时间、原动作、实测位移；
3. 下一次搜索的根状态用实测位姿重建，算法时间不按“完整执行了 1 秒”增加；
4. 不把树里预测的落点写成下一拍状态。

正常走满 1.0 秒时，记 `completed`，算法时间加 1，位置仍用实测值，不用积分值。速度和加速度第一版写入 0。这和 C++ 滚树时每步清零速度一致，只和开局编码接近，不是中段训练分布。不要把 `/odom` 速度写回 29 维状态。

通信丢失、雷达失效、定位失效都不写成 `active = 0`。`active = 0` 只留给 `Example8` 的捕获规则。捕获距离现为中心距 `desired_distance = 1.0` 米。阶段 6 之前用实车外形核对这个值，点模型的 1 米可能已经贴上车体。

### 3.6 未知区域

语义激光没命中时归一化成最大距离。仿真里这表示该方向没有矩形。实车上这只表示这一帧没看到。安全层把未知方向限速或停车。安全膨胀不写回 `m_obstacles`，否则下一轮策略会把临时边界当成真实障碍。

### 3.7 身份和依赖

每台 NUC 一份配置，不写死 36 或蓝 1：

```text
machine_id
robot_team
robot_id
algorithm_index      # 0..3
team                 # {0,1} 或 {2,3}
map_to_algorithm     # 共用的 R、t
operating_window     # 算法框在 map 上的 20 m × 20 m 像
```

阶段 2 之前在本机 Python 安装 CPU 版 PyTorch，并重新编译 `decison_making/code/cpp` 的 bindings。现有 `python3` 没有 `torch`，而加载 `.pt` 走 `torch.load`。推理仍在 Eigen。RTX 2060 留给已有的装甲容器，不把 MCTS 搬上 GPU。

实车入口单独建，不改仿真 `run.py`。新入口里把 `use_minco_dynamics` 设为 `False`，避免 Python `step()` 和 C++ 搜索不一致。搜索本身不读这个标志。

## 4. 阶段

### 阶段 0：核对车端话题，不改算法

目标：确认决策要订阅的话题在真实启动后有数据，并记下点云处理链。

启动 `/nfs/start_base.sh` 和 `/nfs/start_localization.sh`。规划和行为树可以开，但本阶段不发决策速度。录包核对：

| 话题 | 要记下的内容 |
|---|---|
| `/robot_pose` | `frame_id`、频率、与 `map` 的关系、时间戳 |
| `/lidar/pointcloud` | `frame_id` 是否为 `map`、频率、点数、裁切后的空间范围 |
| `/livox/lidar`、`/livox/points` | 近距离点是否还在 |
| `/control/chassis_info` | 四电机在线、电池 |
| `/odom` | 只作对照，不进算法状态 |
| TF `map`、`base_link`、`gimbal` | 与 `define_lidar2gimbal()` 是否一致 |

同时读 `livox_calibration.cpp` 里 `GroundFilter`、`cloudfilter`、`cloud_removal` 的阈值，写成阶段 0 记录。这些过滤会改变“能看见的障碍”，不能假设 `/lidar/pointcloud` 等于原始扫描。

核对 `~/.bashrc` 和 `/etc/robot.conf` 谁先生效。`start_tree.sh` 每个窗格 `source ~/.bashrc`，交互环境下是蓝 1、机器号 36。把实际生效的队伍和编号写进该车配置。

验收：每辆参与试验的车都有一份配置和一段 rosbag。`/robot_pose` 与 `/lidar/pointcloud` 的 `frame_id` 都是 `map`，时间戳可对齐。未启动的节点不记为可用。

### 阶段 1：固定全车共用的 map → algorithm 变换

目标：定出一组 `R`、`t` 和一块 20 米 × 20 米实验窗，让本阶段要用的车都落在 `[-10, 10]` 内。

做法：

1. 用阶段 0 的出生点和准备活动的区域，在 `map` 上画实验窗。窗在算法系中必须正好对应 `x, y ∈ [-10, 10]`，所以窗是 20 米 × 20 米，边与算法轴对齐，或由 `R` 转正。
2. 出生点跨度约 17 米 × 8 米。若试验只用这个范围，平移即可，`R` 取单位阵或 90 度整数旋转。四台车用同一组参数。
3. 写一个只读节点：订阅 `/robot_pose` 和 `/lidar/pointcloud`，发布转换后的调试点和点云，不发速度。
4. 把一辆车开到实验窗四角和窗外 0.5 米。窗内点落在 `[-10, 10]`，窗外点出框。

验收：四台配置文件里的 `R`、`t` 逐项相同。同一根桩在两台车的算法坐标里偏差小于测量误差。不满足时不进入搜索。

### 阶段 2：用转换后的状态跑 C_PUCT，不接电机

目标：证明旧 checkpoint、264 维编码和队伍掩码在 NUC 上能跑，输入已经是算法坐标。

状态：

```text
0:8     四车算法坐标。没有真实队友时，用虚拟点，也必须在框内
8       算法时间，从 0 开始，只在 completed 步上加 1
9:13    active，开局为 1
13:21   速度，填 0
21:29   加速度，填 0
```

每队只调用自己的掩码：

```text
逃逸：solver.policy(problem, state, team={0,1})
追捕：solver.policy(problem, state, team={2,3})
```

264 维仍由 C++ `policy_encoding()` 生成。障碍物这一阶段用空列表或一组固定测试矩形，矩形已经在算法坐标里。空场景的结果不能当成有障碍时的性能。

本阶段比较三件事：

- Python `policy_encoding()` 与 C++ 编码逐元素一致；
- 四个 `.pt` 能经 `torch.load` 装进 Eigen；
- 单次 `policy()` 的耗时。耗时中位数若大于 1 秒，把 `number_simulations` 和 `search_depth` 降到能在 1 秒内返回，并记录降完的参数。深度 100 是仿真里看未来 100 秒，车端第一版不需要。

验收：掩码外的动作是 0。出框的测试状态被判为非法。全程不发布 `/control/cmd_vel`。

### 阶段 3：一辆实车执行动作

目标：转换后的 `Δx、Δy` 能驱动一台底盘，并且遵守 1 秒合同。

只给一台车真实 `/robot_pose`，另外三台继续用虚拟算法坐标。复用 `/nfs/start_base.sh` 的 `rsg_control`。规划和行为树的速度停掉。

```text
Δx、Δy
  -> 算法系速度，除以 1 秒
  -> 乘算法系下的车体 yaw，得到车体 vx、vy
  -> wz = 0
  -> 再限幅
  -> 执行进程以 20–50 Hz 重发，最多 1.0 秒
```

执行进程和搜索进程分开。安全进程订阅 `/livox/points` 或 `/livox/lidar` 以及 `/control/chassis_info`。定位丢失、点云中断、电机离线、人工急停、近距离障碍，都走第 3.5 节的中断记录。

先做四向试验：算法系的 `+x、-x、+y、-y`。车在场地上的位移方向要和算法轴一致，而不是和车头的习惯方向混用。

验收：

- `/control/motion_ctrl_info` 里的合成速度与执行进程发布的一致；
- 命令在 1.0 秒时变为零，搜索变慢也不会把速度保住；
- 人为打断后日志是 `interrupted`，下一拍根状态是实测位姿；
- 走满的一步日志是 `completed`，实测位移与 `Δ` 的误差被记录，不回写网络；
- 搜索进程卡住时，执行进程仍能停车。

### 阶段 4：点云生成算法坐标矩形，先不进搜索

目标：确认 `/lidar/pointcloud` 能变成保守、不过度膨胀的矩形，并且和车、队友分开。

```text
/lidar/pointcloud          frame = map
  -> 同一组 R、t
  -> 去掉地面残留、自车足迹、队友足迹
  -> 高度和距离过滤
  -> 聚类
  -> 每个点簇一个轴对齐矩形
  -> 只保留与实验窗相交的部分
  -> 发布调试图，不调用 C_PUCT
```

矩形用算法坐标的轴对齐框，因为 `Example8` 的障碍就是 `[[xmin, xmax], [ymin, ymax]]`。斜墙用多个矩形盖住，宁可比点簇略大，不要把整个未知区涂成障碍。

挪动一个箱子再录一次。配置文件不改，新位置要出现在下一帧矩形里。地面、自车和站在旁边的队友不能整段变成静态障碍。

验收：矩形在算法坐标里。窗内的箱子被框住。无回波方向保持为空矩形列表，而不是一条封死的墙。这一阶段仍然不把矩形交给搜索。

### 阶段 5：每轮搜索冻结一份快照

目标：C++ 搜索树在一整次 `policy()` 内使用同一份障碍，下次搜索才更换。

在 pybind 和 `C_PUCT._problem_wrapper_for` 上增加显式更新，例如 `update_obstacles(rectangles)`，直接改 C++ `m_obstacles`。不能依赖“改 Python 列表就会被看到”。

```text
取一帧已转换的矩形，记下时间戳
  -> update_obstacles
  -> 本队 policy()
  -> 树内所有未来节点使用这同一份矩形
  -> 返回后丢弃这份快照
下一轮重新取点云
```

搜索开始后到达的新点云不插入当前这棵树。

同时在 C++ 碰撞检查之外保留安全进程。C++ 现在只判断机器人中心点是否落在矩形内，不检查车体足迹，也不检查这一秒位移扫过的区域。安全进程用车体尺寸和制动距离做这件事。安全膨胀不写进快照。

验收：

- 搜索过程中挪箱子，当前这条动作不变；下一次搜索才变；
- 日志能对上快照时间戳和 `policy()` 调用；
- 把车放到矩形中心上，搜索把该状态判为碰撞；
- 只在传感器前方有箱子时，车后方的未知区不会被策略编码成“已确认安全”。安全进程在近距离未知或突然出现的点上仍能打断，并记 `interrupted`。

### 阶段 6：四车，敌方坐标暂时仍由状态接口给出

目标：两队各跑自己的搜索，先不把识别误差混进来。

- 每队一台队长 NUC 跑 C_PUCT，只对自己的 `team` 调用 `policy()`；
- 队长发布本队两辆车的动作，不发布对方动作；
- 每辆车有自己的执行进程和安全进程；
- 四车位姿用阶段 1 的同一组 `R`、`t` 汇成一个 29 维状态；
- 对方下一拍的真实指令不写入本队搜索。对方未来动作由本队树里的策略模型预测；
- 对方当前坐标只作为工程阶段的状态输入，日志里标明 `opponent_pose_source = state_interface`。

捕获由一个状态适配器统一判定，两名队长读同一结果。通信中断时本队停车，并把该车标成 `pose_lost`，不把 `active` 写成 0。

验收：动作不会发到另一台车。两队的算法坐标一致。新障碍只影响看到它的那一队的下一次搜索。任一队长搜索失败时，该队两辆车在 1 秒内停车。

### 阶段 7：用现有装甲结果替换敌方坐标

目标：关闭敌方坐标接口后，敌车位置来自本车传感器。

先读 `/armor_shooting/robot_map`、`/armor_shooting/debug_robot_pose` 的字段、`frame_id`、敌我编号和时间戳。能用就用，再用点云或目标聚类补米制距离。单目框本身不作为距离。

相机仍由 `as_cont` 独占。这一阶段不第二路打开 MVS。只有这些话题没有敌我身份或坐标系不可用时，才停掉 `as_cont`，改 `CaptureWorker` 或单独取流。

先做影子模式：估计坐标只写日志，搜索仍用阶段 6 的状态接口。误差和延迟稳定后，再把估计坐标作为唯一输入，并在日志里确认没有 `opponent_pose_source = state_interface`。

短时丢失用跟踪外推，保持 `active`。长时间丢失则降速或停车，记 `track_lost`，不记成捕获。

云台转动时，观测要经过 `gimbal` 和 `camera` 的 TF 再进 `map`，然后用同一组 `R`、`t`。`base_link → gimbal` 只有 yaw，pitch 在 `/control/gimbal_info` 里，单位是度。

验收：关闭坐标广播后系统仍能跑。多目标不串到错误的算法编号 `0..3`。遮挡后能重新对上。影子模式的误差有记录。

### 阶段 8：用真实观测微调或重训

目标：让策略适应真实点云、执行误差和局部可见性。264 维结构保持不变。

训练分布里加入：局部视场、盲区、漏检、矩形近似误差、1 秒合同的提前中断、车体速度饱和、世界系到车体系的航向误差。价值网络在 `beta_value = 0` 时不是部署依赖。若重新打开它，输入只能是车上实际拿得到的估计状态。

若要把运行窗口扩到超过 20 米 × 20 米，这一阶段重新训练对应的 `state_lims`，不用旧 checkpoint 硬改限幅。

验收：没有完整先验障碍地图，也没有敌方真值广播。雷达提供局部障碍，相机和点云提供敌车，安全层处理未知和突发障碍，多局能够完成追逃。旧权重在空场景上的成功率不作为这项验收。

## 5. 进程划分

| 进程 | 输入 | 输出 | 从哪一阶段开始 |
|---|---|---|---|
| 坐标与状态 | `/robot_pose`、队友位姿、共用 `R,t` | 29 维状态 | 1 |

## 6. 不做的事

- 不把 `Example8` 里那四个仿真矩形搬到场地。
- 不把 `map_size = 10 m` 或 `moving_obstacles` 当成地图。
- 不缩放场地去凑 `[-10, 10]`。
- 不修改 `state_lims` 后加载现有 `.pt`。
- 不在搜索未结束时延长上一条速度。
- 不把安全层提前停车记成 `completed`。
- 不把“语义激光为最大距离”当成可通行。
- 不和规划、行为树同时发自主速度。
- 不第二路打开海康相机、串口或 Livox 驱动。
